# Implementation Prompt: Tier 5 — Knowledge Databases (Opening Book + Endgame Tablebases)

## Goal

Add two knowledge databases to produce a new engine tier that plays perfect chess in the
opening and endgame phases:

1. **Opening Book** — Play pre-computed book moves in the opening instead of searching.
   Saves all thinking time for the middlegame and guarantees theory-correct openings.

2. **Endgame Tablebase Probing** — In positions with few pieces, probe the Lichess Tablebase
   REST API for a perfect evaluation (win/draw/loss with distance to zeroing). This provides
   provably optimal play in any 7-or-fewer-piece endgame.

Wire these into a new `SearchV5` orchestration layer that wraps `SearchV4` and adds pre-search
database probes. Register six new bots (blitz and classical only — bullet games are too short
to benefit).

**Prerequisite**: Tiers 0, 2, 3, and 4 are already applied. The current `BotRegistry.all.length`
is **45**; this tier brings it to **51**.

## Part 1 — Opening Book

### Polyglot file format

A Polyglot `.bin` file is sorted by 8-byte Zobrist key. Each 16-byte entry:
```
bytes 0-7:  Zobrist key (big-endian uint64)
bytes 8-9:  move (big-endian uint16), encoded as:
              bits 0-2:   promotion piece (0=none,1=knight,2=bishop,3=rook,4=queen)
              bits 3-8:   to-square (0=a1..63=h8)
              bits 9-14:  from-square
              bit 15:     always 0
bytes 10-11: weight (big-endian uint16) — relative probability
bytes 12-15: learn data (ignored)
```

### Polyglot move decoding — CASTLING IS A SPECIAL CASE

Polyglot encodes castling as **king-to-rook square**, not king-to-target square:

| Castling | Polyglot encoding | This engine's UCI |
| --- | --- | --- |
| White O-O | e1h1 | e1g1 |
| White O-O-O | e1a1 | e1c1 |
| Black O-O | e8h8 | e8g8 |
| Black O-O-O | e8a8 | e8c8 |

When matching the decoded `(from, to, promo)` against the legal-move list:

1. If the piece on `from` is a king and `(from, to)` is one of the four king-to-rook patterns
   above, rewrite `to` to the king's destination square before searching the move list.
2. Otherwise, match `(from, to, promo)` directly against the generated legal moves.

Failing to handle this means the engine will silently fall through to search whenever the book
prescribes castling — a frequent occurrence after move 6–8 in most openings.

### Polyglot Zobrist (separate from `Zobrist.scala`)

The Polyglot key uses a **fixed published table** of 781 64-bit constants (`Random64`),
*not* values generated by a local PRNG. The implementer MUST copy the literal Random64 array
from `https://www.chessprogramming.org/Polyglot` (the "PolyGlot Hash Calculation" section
embeds the full hex table). Storing the literal bytes is the only way the resulting keys will
match real Polyglot book files bit-for-bit.

Index layout in `Random64`:
- `0..767` — piece × square. Polyglot piece ordering (NOT the engine's):
  `bpawn=0, wpawn=1, bknight=2, wknight=3, bbishop=4, wbishop=5,
   brook=6, wrook=7, bqueen=8, wqueen=9, bking=10, wking=11`.
  Index: `Random64[piecePolyIdx * 64 + square]`, with squares using a1=0…h8=63.
- `768..771` — castling. **Four independent XOR slots**: white-O-O, white-O-O-O, black-O-O,
  black-O-O-O. XOR each slot **only if that specific right is still available** in
  `pos.castlingRights`. Do NOT index `Random64[768 + castlingRights]` — that is the most
  common implementation mistake and it produces keys that are wrong for every position except
  the starting position.
- `772..779` — en-passant file. XOR `Random64[772 + file(epSquare)]` **only if a pawn of the
  side to move can actually capture en passant on this turn** (i.e. an adjacent same-rank
  pawn of the side to move exists). The starting position has no ep square, so the
  starting-position regression test passes even if this rule is ignored — but every position
  after a double pawn push is wrong without this guard.
- `780` — side to move. XOR `Random64[780]` if and only if `pos.sideToMove == Col.White`.

**Three regression tests** — these three keys catch nearly every implementation bug:

| Position | Key |
| --- | --- |
| Starting position | `0x463b96181691fc9c` |
| After `1. e4` | `0x823c9b50fd114196` |
| After `1. e4 d5` | `0x0756b94461c50fb0` |

The single starting-position test is insufficient: it does not exercise the ep-only-if-capture
rule, the turn XOR, or the castling decoder.

### New file: `chess/OpeningBook.scala`

```scala
object OpeningBook:
  def probe(pos: Position): Option[String]                       // returns UCI move or None
  private[chess] def probeBuffer(pos: Position,
                                 buf: ByteBuffer): Option[String]  // testability hook
```

Implementation notes:
1. Load `books/performance.bin` from the classpath once into a `lazy val Option[ByteBuffer]`.
   If missing, log a single warning and return `None` on every subsequent probe (graceful
   degradation). The classpath read is one-shot and synchronous; no ZIO effect needed here.
2. Exit early without computing the Polyglot key when `pos.fullMoveNumber > 30`.
3. Compute the Polyglot key using `PolyglotZobrist`.
4. Binary-search the file for the lowest-index entry with that key, then scan forward over
   the contiguous block of equal keys.
5. Collect all matching entries; if total weight is zero, return `None`. Otherwise, sample a
   single entry with probability proportional to its weight using `scala.util.Random.nextInt`.
6. Decode the move (apply the castling rewrite from above), scan the generated legal moves for
   one with the matching `(from, to, promo)`, and verify with `LegalCheck.isLegal`.
7. If no legal match is found, return `None`. Do NOT fall back to a different book entry — the
   caller's downstream search will produce a better move than a random other book entry.

Returns:
- `Some(uci)` — a legal book move
- `None` — out of book (no entry, post-move-30, missing resource, or decode/legality failure)

### New file: `chess/PolyglotZobrist.scala`

Store the literal 781-entry `Random64` table as a private `val`. Expose:

```scala
object PolyglotZobrist:
  def key(pos: Position): Long
```

Compute by XOR-folding the indices described in the layout section above. Use the engine's
`Pieces.colorOf` / `Pieces.typeOf` to map mailbox values to Polyglot piece indices, and
`Position.pieceBB(Col.<side>, PType.Pawn)` plus `Attacks.pawnAttacks` to check the
"can-actually-capture-EP" condition.

## Part 2 — Endgame Tablebase Probing

### Data source: Lichess Tablebase API

Endpoint: `GET https://tablebase.lichess.ovh/standard?fen=<URL-encoded FEN>`

Response JSON (relevant fields):
```json
{
  "category": "win" | "cursed-win" | "draw" | "blessed-loss" | "loss",
  "dtz": -50,
  "moves": [
    { "uci": "e1e2", "dtz": 10, "zeroing": false, "category": "loss" },
    ...
  ]
}
```

**The `moves` array is already sorted by Lichess from the side-to-move's perspective**: the
first entry is the best move. Do not re-rank locally. If the array is empty (terminal
position), return `None`.

**Rate limit**: Lichess allows ~5 req/s per IP. A single chess game makes at most one probe
per move, far under the limit; no client-side throttling needed.

### Architectural placement

Place the tablebase client **outside `chess/`** — it performs HTTP I/O and uses ZIO effects,
violating the chess-package's pure-and-self-contained invariant. Use a new package:

```
maichess.engine.service.clients.TablebaseClient        (trait)
maichess.engine.service.clients.TablebaseClientLive    (real implementation)
```

The trait makes the client mockable for tests; placement under `service/` brings it under the
standard 100% statement-coverage rule.

### New file: `service/clients/TablebaseClient.scala`

```scala
package maichess.engine.service.clients

import zio.{IO, ZIO}

final case class TablebaseResult(bestMove: String, evaluationCp: Int)

trait TablebaseClient:
  // Never fails — returns ZIO.none for piece-count > 6, network errors, timeouts, or
  // parse failures so the caller can fall through to opening book / search.
  def probe(fen: String, pieceCount: Int): IO[Nothing, Option[TablebaseResult]]
```

Score mapping (engine perspective; the `category` and `dtz` in the response are already from
the side-to-move's viewpoint):
- `win`         → `+20000 - dtz`   (prefer fastest win)
- `cursed-win`  → `+5000`
- `draw`        → `0`
- `blessed-loss`→ `−5000`
- `loss`        → `−20000 + dtz`   (prefer longest resistance)

### `TablebaseClientLive` implementation

- Short-circuit: if `pieceCount > 6`, return `ZIO.none` without touching the network.
- Use `java.net.http.HttpClient` (no new dependency). `HttpClient.send` is blocking — wrap in
  `ZIO.attemptBlocking`, not `ZIO.attempt`.
- URL-encode the FEN: `URLEncoder.encode(fen, StandardCharsets.UTF_8)`.
- Apply `.timeout(2.seconds)`.
- Convert *every* failure mode (`IOException`, timeout, non-200 status, parse failure) to
  `ZIO.none` via `.catchAll(_ => ZIO.none).map(_.flatten)` so the effect never fails.
- Build the result from `parseResponse(json)`.

Expose the parser as a pure top-level function in the companion object so it is unit-testable
without HTTP:
```scala
object TablebaseClientLive:
  def parseResponse(json: String): Option[TablebaseResult] = ...
```

JSON parsing: simple known-shape JSON. Either add `"com.lihaoyi" %% "ujson" % "3.x"` to
`build.sbt`, or use a small hand-written extractor (the response shape is fixed; regex on
`"uci":"<value>"` and `"category":"<value>"` is acceptable for this scope).

Provide a `ZLayer.succeed[TablebaseClient](new TablebaseClientLive())` in the companion.

### New file: `service/SearchV5.scala`

Lives in `service/`, not `chess/`, because it composes ZIO effects (the tablebase probe).

```scala
package maichess.engine.service

import zio.{IO, ZIO}
import maichess.engine.chess.{Move, OpeningBook, Position, SearchV4}
import maichess.engine.service.clients.TablebaseClient

final class SearchV5(tablebaseClient: TablebaseClient):
  private val inner = new SearchV4()

  def bestMove(pos: Position, fen: String, timeLimitMs: Long): IO[String, (String, Int)] =
    val pieceCount = java.lang.Long.bitCount(pos.occupied)
    for
      tb <- tablebaseClient.probe(fen, pieceCount)
      result <- tb match
        case Some(r) =>
          ZIO.succeed((r.bestMove, r.evaluationCp))
        case None =>
          OpeningBook.probe(pos) match
            case Some(uci) =>
              ZIO.succeed((uci, 0))
            case None =>
              ZIO.attempt(inner.bestMove(pos, timeLimitMs))
                .mapError(e => s"Search failed: ${e.getMessage}")
                .flatMap { case (mv, sc) =>
                  if mv == Move.None then ZIO.fail(s"No legal moves in position: $fen")
                  else                    ZIO.succeed((Move.toUci(mv), sc))
                }
    yield result
```

Note the `IO[String, (String, Int)]` error channel — matches the existing branches in
`EngineServiceLive.runSearch`.

takes longer. Choose one and use it everywhere (descriptions, probe threshold, and tests):

- Alternative: probe at `pieceCount ≤ 6`, change descriptions to say "six or fewer pieces" in

## Constraints

- The book file (`performance.bin`) must be committed to the repository; verify size < 5 MB
  and license compatibility (public domain) before commit.
- The `TablebaseClient` trait must never expose a failure channel — the live client converts
  all errors and timeouts to `ZIO.none` so the caller can always fall through.
- All HTTP calls have a 2-second timeout; blocking calls are wrapped in `ZIO.attemptBlocking`.
- The piece-count guard (`pieceCount > N` → skip API call) lives **inside the live client**,
  not in `SearchV5`, so a future caller cannot accidentally bypass it.
- The `chess/` package contains no I/O, no ZIO effects, and no HTTP. Put `SearchV5` and
  `TablebaseClient` under `service/`.
- The Polyglot Zobrist `Random64` table must be the literal published constants — verified by
  three regression keys (start, post-`1. e4`, post-`1. e4 d5`), not just the starting position.
- Do not cache tablebase responses — adds complexity without benefit at this traffic scale.
- Do not modify `build.sbt` for resource paths (sbt picks up `src/main/resources` by default).
- Do not add new dependencies unless necessary; prefer `java.net.http.HttpClient` over `sttp`.
